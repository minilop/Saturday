Analyze and trace the business context around a specific point in an existing
  codebase. Use when the user wants to understand which business processes
  use, depend on, or are affected by a specific database table, field, entity,
  class, method, API, event, Job, external table, data source, or configuration.
  Start from the user's specified point and expand outward through code
  references, call relationships, data flows, dependencies, and related
  business operations to identify and explain the connected business logic.


Start from a specific point in the codebase and trace outward to identify the related business processes, dependencies, and data flows.

Use this skill when the user wants to understand the business context and related logic around a specific point in the codebase.

Typical starting points include:

- a database table or entity
- a specific field or column
- a class or method
- an API or endpoint
- a message topic or event
- a Job or scheduled task
- an external table or external data source
- a configuration value
- a specific piece of code


## Workflow

### 1. Understand the Request

Identify the point or business context that the user wants to investigate.

### 2. Explore the Codebase

Use `code-explorer` to find relevant code, references, call relationships, data flows, and dependencies.

### 3. Analyze the Business Context

Provide the exploration results to `business-analyzer`.

Ask it to identify the related business processes and explain their relationships.

### 4. Review the Analysis

Provide the code exploration results and business analysis to `business-reviewer`.

Ask it to verify:

- important business conclusions
- code relationships
- data flows
- dependencies
- missing paths
- unsupported assumptions

### 5. Refine the Analysis

If the reviewer identifies issues:

1. Update the business analysis.
2. Address the review findings.
3. Return to Step 4.

Repeat the review cycle for at most 2 iterations.

If significant issues remain after the maximum iterations, record them as unresolved issues instead of continuing the loop.

After the analysis has passed review, **MUST generate a Markdown file** containing the final verified business analysis.

Do not output the full analysis only in the chat response.

#### Output Path

Create the Markdown file under:

`business-analysis/`

relative to the project root.

If the directory does not exist, create it.

Use a descriptive filename based on the analysis target:

`business-analysis/<target>.md`

For example:

- `business-analysis/EXT_CUSTOMER.md`
- `business-analysis/customer-table.md`
- `business-analysis/order-cancel.md`

Generate a Markdown file containing the verified business analysis.

The document must include:

1. Analysis target
2. Business overview
3. Business logic diagram
4. Related business processes
5. Detailed business flow
6. Key code locations
7. Data flow and dependencies
8. External tables or external systems, when applicable
9. Unresolved or uncertain points

Use a Mermaid diagram to visualize the business logic and relationships.

Include a table of key code locations with at least:

| ID | File | Class / Method | Line | Evidence | Business Relevance |
|---|---|---|---:|---|---|

Every important business conclusion should be traceable to one or more code locations.

The generated Markdown file is the primary output of the analysis.

## Analysis Principles

### Code Is the Source of Truth

Base the analysis on the actual implementation in the codebase.

Do not infer business behavior solely from names, comments, documentation, or assumptions.

### Separate Facts and Interpretation

Distinguish between:

- behavior directly confirmed by the code
- business interpretation based on the code and surrounding context
- behavior that cannot be determined from the code

Do not present an interpretation as a confirmed fact.

### Key Code Locations Are Evidence

Do not include every discovered reference in the final document.

Select only code locations that directly support an important business conclusion.

A key code location should be included when it provides evidence for one or more of the following:

- the entry point of a business process
- a database read or write
- an external table or external system access
- a state transition
- an important business condition
- a significant data transformation
- a call that connects major business components
- an event or message that affects the business flow

For each selected location, explain what the code does and why it is relevant to the business analysis.

For example, if the analysis finds that an external table is used by a customer synchronization process, the final document should contain only the code locations that support this conclusion:

| ID | File | Class / Method | Line | Evidence | Business Relevance |
|---|---|---|---:|---|---|
| E1 | `CustomerSyncJob.java` | `execute()` | 42 | Starts the synchronization process | Business entry point |
| E2 | `CustomerRepository.java` | `findCustomers()` | 125 | Reads from `EXT_CUSTOMER` | External data source |
| E3 | `CustomerSyncService.java` | `sync()` | 78 | Processes the retrieved customer data | Business processing |
| E4 | `CustomerRepository.java` | `save()` | 156 | Updates the internal `Customer` table | Business state change |

Do not include unrelated or redundant references only because they were found during code exploration.

For example, the following would be too broad:

| File | Class / Method | Line | Reason for Exclusion |
|---|---|---:|---|
| `Customer.java` | `getId()` | 20 | Getter does not support an important business conclusion |
| `Customer.java` | `getName()` | 30 | Getter does not explain the business flow |
| `CustomerRepository.java` | `findById()` | 140 | Not relevant to the analyzed synchronization flow |
| `CustomerRepository.java` | `exists()` | 150 | Does not contribute to the identified business logic |
| `CustomerUtils.java` | `formatName()` | 35 | Utility implementation is not relevant to the business conclusion |

Prefer a small number of meaningful code locations over a large list of references.

The selected code locations should be sufficient for another developer to verify the main business conclusions without reading every related reference.

### Trace Relationships

Do not stop at direct references.

Follow relevant callers, callees, data flows, database operations, events, Jobs, and external services when they contribute to understanding the requested business context.

### Keep the Scope Relevant

Do not analyze unrelated framework code, utilities, or infrastructure.

Focus on code that contributes to the requested business context.

### 3. `business-reviewer.agent.md`

```markdown
---
name: business-reviewer
description: Review a business logic analysis against the actual code evidence. Identify unsupported assumptions, incorrect business interpretations, missing relationships, missing evidence, and inconsistencies between the analysis and the implementation.
---

# Business Reviewer

## Purpose

Verify that the business analysis is sufficiently supported by the actual code evidence.

The reviewer must focus on correctness, evidence, completeness, and scope.

## Responsibilities

- Verify important business conclusions.
- Verify code relationships.
- Verify data flows.
- Verify external table and external system usage.
- Verify key code evidence.
- Identify missing important paths.
- Identify unsupported assumptions.
- Identify irrelevant or redundant evidence.

## Workflow

### 1. Review the Code Evidence

Examine the findings from `code-explorer`.

Use the actual code locations as the source of truth.

### 2. Verify Business Conclusions

For each important business conclusion from `business-analyzer`, determine whether the provided Evidence IDs actually support it.

Check:

- Does the referenced code perform the described operation?
- Does the call relationship actually exist?
- Does the data flow match the analysis?
- Is the business interpretation stronger than what the code supports?

### 3. Verify External Resources

When external tables or systems are involved, verify:

- whether the resource is actually external
- where it is accessed
- which component accesses it
- how the data is used
- whether the claimed business process actually depends on it

Do not accept an external-resource classification based only on naming.

### 4. Check for Missing Relationships

Determine whether important relationships were missed.

Check for:

- additional usages
- alternative callers
- additional business processes
- downstream processing
- upstream data sources
- events or messages
- database writes
- external dependencies

Only report missing relationships when they materially affect the requested business analysis.

### 5. Check Key Code Evidence

Verify that the selected key code locations are:

- directly relevant
- sufficient to support the business conclusions
- not merely incidental references
- not redundant

Identify important conclusions that lack sufficient evidence.

### 6. Check Business Scope

Make sure the analysis does not include unrelated code or business processes.

### 7. Return Review Results

Return:

- confirmed findings
- incorrect findings
- unsupported conclusions
- missing relationships
- missing evidence
- irrelevant evidence
- recommended corrections

Do not rewrite the entire business analysis.

Focus on issues that require correction or confirmation.



## Project Context

This project is an existing AWS-based system being migrated to GCP.

The migration replaces AWS services with corresponding GCP services
while preserving the existing business logic as much as possible.

When analyzing business logic:

- Consider both the original AWS services and their GCP replacements.
- Identify where AWS-specific services are used in the existing code.
- Identify the corresponding GCP services used or intended after migration.
- Determine which business processes depend on these services.
- Distinguish migration-related implementation changes from actual business logic changes.
- Do not assume that an AWS service and its GCP replacement have identical behavior.

## Agent Delegation

This skill uses specialized subagents to perform the analysis.

The main agent is responsible for orchestration and final document generation.

The main agent MUST delegate:

- code exploration to `code-explorer`
- business interpretation to `business-analyzer`
- review and verification to `business-reviewer`

Each subagent should focus on its assigned responsibility.
